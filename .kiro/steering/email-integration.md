# IZG Mail Service — Client Integration Guide

This steering file explains how to integrate any client application with the IZG Mail Service for sending emails.

## Environment Behaviour

The mail service handles test vs production automatically — **client apps don't need to do anything different**. You build your integration once and it works in both environments.

In non-production (`APP_ENV != production`), the service automatically:
- Prepends `[TEST]` to the email subject
- Injects a visible yellow "TEST EMAIL" banner at the top of the HTML
- Force-BCCs the IZG team on every email
- Uses a test-specific from address

This means you'll always know when an email came from a test environment without any client-side logic.

### Migration Checklist

When you migrate a client app to use this mail service, the following environment variables from the client app can be **removed** after migration is complete:
- `RESEND_API_KEY` — no longer needed, the mail service owns the Resend key
- Any `FROM_EMAIL` / `FROM_NAME` variables — controlled by the mail service
- Any email template files or HTML builders — templates live in the mail service DB

Let your admin (Makungu) know once migration is done so the old variables can be cleaned up from Vercel.

### Internal Testing Override (IZG Dev Use)

Before handing a site to the client for testing, you'll want all emails to go to your own inbox regardless of what address the user typed on the frontend. The **client app** handles this — the mail service doesn't need to know.

1. Add an environment variable to the **client app**:
   ```env
   IZG_MAIL_OVERRIDE_TO=your-dev-email@yourdomain.com
   ```

2. In your email sending logic, check the override and swap the `to` field:
   ```typescript
   const overrideTo = process.env.IZG_MAIL_OVERRIDE_TO;

   const res = await fetch(process.env.IZG_MAIL_URL!, {
     method: "POST",
     headers: {
       "Content-Type": "application/json",
       "x-izg-token": process.env.IZG_MAIL_TOKEN!,
     },
     body: JSON.stringify({
       to: overrideTo || formData.email,  // override wins if set
       subject: "Booking Enquiry",
       template: "contact-form",
       variables: {
         name: formData.name,
         email: formData.email,  // original email still visible in the body
         phone: formData.phone,
         message: formData.message,
       },
     }),
   });
   ```

3. When the override is set, every email goes to your inbox. The real recipient's address is still captured in the template variables so you can see who it would have gone to.

4. **Before client handover:** Remove the `IZG_MAIL_OVERRIDE_TO` env var from the client app's Vercel project. No code changes needed — when it's `undefined`, the real `to` address passes through.

**Env vars to remove after handover:**
- `IZG_MAIL_OVERRIDE_TO`

## Setup

Add the following environment variable to your client project:

```env
IZG_MAIL_TOKEN=<your-client-token>
IZG_MAIL_URL=https://izg-mail-service.vercel.app/api/send
```

Your token is generated by the IZG Mail Service admin when your client is registered. Contact your admin if you don't have one.

## Sending an Email

Make a POST request to the mail service endpoint:

```typescript
const res = await fetch(process.env.IZG_MAIL_URL!, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "x-izg-token": process.env.IZG_MAIL_TOKEN!,
  },
  body: JSON.stringify({
    to: "recipient@example.com",
    subject: "Contact Form Submission",
    template: "contact-form",
    variables: {
      name: "John Doe",
      email: "john@example.com",
      phone: "072 123 4567",
      message: "I'd like to enquire about your services.",
    },
  }),
});

const data = await res.json();
// Success: { ok: true, id: "resend-message-id" }
// Error: { error: "description of what went wrong" }
```

## API Fields

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `to` | `string \| string[]` | yes | Recipient email(s) |
| `subject` | `string` | yes | Email subject line |
| `template` | `string` | yes | Template slug (e.g. `"contact-form"`, `"welcome"`) |
| `variables` | `object` | no | Key-value pairs injected into the template `{{placeholders}}` |
| `text` | `string` | no | Plain text fallback |
| `replyTo` | `string` | no | Reply-to address (e.g. the person who submitted a form) |
| `cc` | `string \| string[]` | no | CC recipients |
| `bcc` | `string \| string[]` | no | BCC recipients |
| `tags` | `object` | no | Metadata key-value pairs for tracking |
| `scheduledAt` | `string (ISO 8601)` | no | If set, email is queued for future delivery |

## Authentication

Every request must include the `x-izg-token` HTTP header with your client token:

```
x-izg-token: your-32-character-token-here
```

## Response Codes

| Code | Meaning |
|------|---------|
| `200` | Email sent successfully |
| `202` | Email scheduled for future delivery |
| `400` | Bad request (missing required fields, invalid date) |
| `401` | Missing token |
| `403` | Invalid or inactive token |
| `422` | Unprocessable (template not found, missing variables, send failure) |
| `500` | Internal server error |

## Available Templates

Check the IZG Mail Service dashboard at `/dashboard/templates` to see all available templates, their required variables, and HTML previews.

Common templates:
- `contact-form` — requires: `name`, `email`, `phone`, `message`
- `welcome` — requires: `name`, optional: `customMessage`

## Scheduling Emails

To schedule an email for future delivery, include `scheduledAt` with an ISO 8601 date string:

```typescript
body: JSON.stringify({
  to: "recipient@example.com",
  subject: "Your weekly digest",
  template: "weekly-digest",
  variables: { ... },
  scheduledAt: "2026-08-15T09:00:00.000Z",
})
```

The service processes scheduled emails via a daily cron job (06:00 UTC). All emails with `scheduledAt` in the past are sent in one batch.

## Creating Templates (Admin API)

Templates are created via the admin API. Authentication uses the same `x-izg-token` client token used for sending emails — the template is automatically associated with that client.

**Endpoint:** `POST {{BASE_URL}}/api/admin/templates`

**Headers:**
```
Content-Type: application/json
x-izg-token: <your-client-token>
```

**Body:**
```json
{
  "slug": "contact-form",
  "name": "Contact Form Notification",
  "description": "Sent when someone submits a contact form",
  "html": "<!DOCTYPE html><html><head><meta charset=\"utf-8\"></head><body style=\"font-family: -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif; max-width: 600px; margin: 0 auto; padding: 20px;\"><img src=\"{{imageBaseUrl}}/logo.png\" alt=\"Logo\" width=\"120\" /><h2 style=\"color: #1a1a1a;\">New enquiry from {{name}}</h2><table style=\"width: 100%; border-collapse: collapse; margin-top: 16px;\"><tr><td style=\"padding: 8px 0; font-weight: 600; color: #555;\">Email:</td><td style=\"padding: 8px 0;\">{{email}}</td></tr><tr><td style=\"padding: 8px 0; font-weight: 600; color: #555;\">Phone:</td><td style=\"padding: 8px 0;\">{{phone}}</td></tr><tr><td style=\"padding: 8px 0; font-weight: 600; color: #555; vertical-align: top;\">Message:</td><td style=\"padding: 8px 0;\">{{message}}</td></tr></table><hr style=\"margin-top: 24px; border: none; border-top: 1px solid #eee;\"><p style=\"font-size: 12px; color: #999;\">Sent via IZG Mail Service</p></body></html>",
  "requiredVariables": ["name", "email", "phone", "message"],
  "category": "transactional"
}
```

No `clientId` field needed — the client is identified automatically from the token.

**Updating a template:** `PATCH {{BASE_URL}}/api/admin/templates/<template-id>` — same `x-izg-token` header. The endpoint verifies the template belongs to the client before allowing the update. Body contains only the fields you want to change.

**Fields:**

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `clientId` | `string (UUID)` | yes | The client this template belongs to |
| `slug` | `string` | yes | Unique per client (e.g. `"contact-form"`) |
| `name` | `string` | yes | Human-readable name |
| `description` | `string` | no | What this template is for |
| `html` | `string` | yes | Full email HTML with `{{variable}}` placeholders |
| `requiredVariables` | `string[]` | no | Variables that must be provided when sending |
| `category` | `string` | no | One of: `general`, `transactional`, `marketing`, `notification` |

**Note:** The same slug can exist across different clients (e.g. two clients can both have a `"contact-form"` template). At send time, the template is resolved by slug + the client identified by `x-izg-token`.

**Categories:**
- `general` — generic communications
- `transactional` — triggered by user action (contact form, order confirmation)
- `marketing` — campaigns, newsletters
- `notification` — system alerts, status updates

## HTML Template Guidelines

If you are creating templates for the mail service (backend only), follow these rules for email-safe HTML:

1. **Use inline styles only** — no `<style>` blocks or external CSS. Email clients strip them.
2. **Use table-based layout** for complex structures. Flexbox/grid are not supported in most email clients.
3. **Max width 600px** — standard email content width.
4. **Use system fonts** — `-apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif`
5. **Images** — use absolute URLs. Reference `{{imageBaseUrl}}` which is auto-injected per client:
   ```html
   <img src="{{imageBaseUrl}}/logo.png" alt="Logo" width="120" />
   ```
6. **Always include alt text** on images.
7. **Use `{{variable}}` syntax** for placeholders. Double curly braces, alphanumeric + underscore only.
8. **Test with Litmus or Email on Acid** if possible, or at minimum test in Gmail, Outlook, and Apple Mail.

## Error Handling in Client Apps

Always wrap your email send in a try-catch and handle gracefully:

```typescript
export async function sendEmail(payload: EmailPayload): Promise<boolean> {
  try {
    const res = await fetch(process.env.IZG_MAIL_URL!, {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "x-izg-token": process.env.IZG_MAIL_TOKEN!,
      },
      body: JSON.stringify(payload),
    });

    if (!res.ok) {
      const error = await res.json();
      console.error("[email] Send failed:", error);
      return false;
    }

    return true;
  } catch (err) {
    console.error("[email] Network error:", err);
    return false;
  }
}
```

Do not block user-facing flows on email success. Fire-and-forget is fine for notifications; for critical emails (e.g. password reset), check the return value and retry or alert.
